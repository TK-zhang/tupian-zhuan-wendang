# 扩展迭代 PRD - Iteration 8：多模态知识库混合检索与自愈反哺飞轮

## 1. 迭代概述与交付目标

### 1.1 业务诉求
当企业通过系统将成百上千张散乱照片与录像重构为数十篇文档后，文档库的资产价值必须转化为**“企业级多模态知识大脑”**。
单纯的静态文档无法满足高频业务查询，而传统 RAG（检索增强生成）在专业垂直领域存在两大致命缺陷：
1. **纯向量检索的失真**：对精确的代码符号、IP 地址、财务数值、数据库主外键的召回极不可靠；
2. **知识资产单向固化**：用户在问答中发现并指出了某个参数错误，系统无法反哺修复底层文档，导致错误在后续使用中反复出现。
Iteration 8 的核心使命是构建**“四路多模态混合检索内核与闭环自愈反哺飞轮（The Closed-Loop Feedback Flywheel）”**：
不仅支持毫秒级的证据可信问答，更能在用户指正错误时生成增量补丁（AST Delta Patch），反向级联自愈底层 Word/Markdown 文档与全局实体图谱，让知识库具备“越用越准确、持续自演进”的生命力。

### 1.2 阶段验收核心指标
1. **精确技术实体召回率**：针对 IP 地址、数据库字段名、错误码、代码函数的精确查询，**召回率 $100\%$**；
2. **模糊自然语言检索 Top-5 命中率**：在无序语意提问下，包含正确答案证据切片的 Top-5 召回率 $\ge 92\%$；
3. **问答反哺底层文档补丁生效耗时**：从用户在问答界面确认纠错到底层 Word/Markdown 文件物理修正完成，耗时 $\le 200\text{ms}$，且格式与样式**零破坏**。

## 2. 详细功能需求规格 (Functional Requirements)

### FR-801: 四路多模态统一混合检索内核 (Unified 4-Way Hybrid Retrieval Engine)
- **处理逻辑**：
  - **第一路：SQLite FTS5 稠密词法全文索引**
    - 负责极速精准匹配：专有名词、代码块变量、微服务端口、错误日志栈；
  - **第二路：HNSW 离线密集语义向量索引**
    - 采用轻量级离线 Embedding 模型（如 BAAI/bge-m3），负责理解意图模糊的自然语言提问；
  - **第三路：实体图谱拓扑关系检索 (Graph Triple Lookup)**
    - 提取 `<模块A, 调用接口, 模块B>` 等三元组，支撑“哪些模块依赖鉴权服务”的跨文档多跳关联推理；
  - **第四路：视觉图表倒排特征索引 (Visual BBox Index)**
    - 针对用户“找那张蓝色的数据库架构图”或“找包含 3 个分支的时序图”等视觉特征查询，实现直接命中；
  - **倒数融合（Reciprocal Rank Fusion, RRF）**：将四路结果通过自适应权重加权，输出最终精排证据列表。

### FR-802: 具身证据溯源问答引擎 (Evidence-Grounded Q&A Engine)
- **处理逻辑**：
  - 推理引擎仅以召回的 DocAST 节点与图表切片为上下文边界（Prompt Context-Grounded）；
  - **严禁无依据推测**：若证据中缺失对应信息，系统强制回答“现有重构文档及原始素材中未找到关于该参数的记录”，坚决阻断大模型胡编乱造；
  - **交互式证据卡片挂载**：回答中的每一个事实论据后，自动附带 `[证据卡片 #1]` 交互标签；用户悬浮或点击时，即时弹出原始原片高精截面与红框定位。

### FR-803: 交互反馈增量自愈补丁机制 (AST Delta Patch Cascading Self-Healing)
- **处理逻辑**：
  - **用户纠错触发**：当用户在问答界面提出异议（例如用户标注：“图中的端口实际上是 9092，不是 9090”）；
  - **Delta Patch 编译器**：
    - 系统解析用户纠错意图，生成符合 RFC 6902 标准的 JSON 增量补丁；
    - 自动定位目标文档的 `block_id` 与属性路径（如 `/table_data/grid/2/1/text`）；
  - **底层文档物理自愈**：
    - 调用 DocAST 更新接口，原子化应用该 Patch；
    - 触发增量编译管线，同步无损更新磁盘上的 `.docx` 与 `.md` 文件；
    - 同步更新 SQLite FTS5 与向量索引，保证后续查询立即体现最新纠错结果。

### FR-804: 查询模式感知与文档群自演进优化器 (Self-Evolving Document Optimizer)
- **处理逻辑**：
  - **提问热点统计**：后台匿名记录用户在知识库中的高频追问主题与未命中关键词；
  - **大纲结构演进建议**：
    - 若发现用户连续多次在不同文档间追问“接口幂等性如何处理”，系统判定该主题跨文档离散且关注度极高；
    - 自动在管理控制台提出重构优化建议：“检测到高频关注主题【接口幂等性】，建议将其抽离为独立章节或自动生成对比汇总表格”。

## 4. 边界场景与异常防御矩阵

| 边界场景 | 现象描述 | 确定性防御方案 |
| :--- | :--- | :--- |
| **冲突补丁（并发人工修改）** | 两个用户在问答中对同一个配置项给出了不同的纠错内容 | 引入乐观锁（Optimistic Locking）与版本号（`ast_version`）：检测到版本冲突时挂起补丁并推送至管理员审核池 |
| **虚假/恶意用户纠错** | 用户故意在问答中输入错误常识，试图污染知识库 | 设置纠错置信度阈值：要求提供文字依据或由高级审计员审批方可持久化落盘至物理 Word 文件 |
| **全量重新索引开销过高** | 每次修改一个端口号就重新跑全库嵌入，导致 GPU 被占满 | 强制采用增量索引更新（Incremental Ingestion）：仅对受影响的单个 Block 执行哈希刷新与局部向量 Upsert |
